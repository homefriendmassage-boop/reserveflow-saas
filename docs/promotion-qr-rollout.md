# โปรโมชั่นตกกุ้งและ QR ใช้ครั้งเดียว

PR #5 ใช้ branch `feature/shrimp-hour-promos-qr-redemption` สำหรับทดสอบและรีวิวก่อนเปิดใช้งาน

## เส้นทางที่รองรับ

| จอง | ราคาปกติเมื่อร้านตั้ง 120 บาท/ชม. | ตัวอย่างส่วนลด | ตัวอย่างของแถมที่ราคาปกติ |
| --- | ---: | ---: | --- |
| 1 ชม. | 120 | 120 | — |
| 2 ชม. | 240 | 220 | น้ำ 1 ขวด |
| 3 ชม. | 360 | 300 | เครื่องดื่มไม่เกิน 40 บาท |
| 4 ชม. | 480 | 380 | ของทานเล่นไม่เกิน 59 บาท |
| 5 ชม. | 600 | 450 | อาหารไม่เกิน 89 บาท |

- Owner/Admin ตั้งโปรใน `promotion-manager.html` แยกตามร้าน กำหนดสถานะ วันเริ่ม วันสิ้นสุด และจำนวนสิทธิ์ได้ ตั้งราคาปกติของหมวดรายชั่วโมงให้ตรงกับแพ็กเกจของแถม ค่าบริการของหมวดคิดครั้งเดียว
- ลูกค้าเลือกได้หนึ่งแพ็กเกจที่ตรงจำนวนชั่วโมง หรือใช้ราคาทั่วไปของหมวด โปรของแถมคิดราคาเต็มและไม่ซ้อนส่วนลดของหมวด ราคาของแพ็กเกจและของแถมถูกเก็บเป็นข้อมูล ณ เวลาจอง
- ใบเสนอราคาสงวนโควต้า 15 นาทีและผูกกับข้อมูลจองเดิม การยกเลิกใบเสนอราคาคืนโควต้าที่ยังไม่ผูกกับการจอง การตรวจช่วงเวลาและความจุยังใช้กติกาจองเดิมทั้งตอนเสนอราคาและตอนบันทึกจริง
- การตรวจสลิปที่ผ่านและตรงยอดจึงออกคูปองสำหรับโปรของแถมหนึ่งใบต่อรายการ การเปลี่ยนสถานะเป็นยืนยันในหลังบ้านอย่างเดียวไม่ออกคูปอง รายการที่ใช้เส้นทางตรวจด้วยมือยังต้องรอหลักฐานยืนยันที่ระบบรองรับก่อนออกของแถม
- ลูกค้าเปิดคูปองจากบัตรจองได้ เมื่อจองผ่าน LIFF ที่ยืนยันตัวตนแล้ว คิวส่ง Flex จะเลือก token ของ OA ร้านจาก Vault ระบบบันทึกว่า LINE API รับคำขอเมื่อ API ตอบรับ คำตอบนี้ยังไม่ยืนยันว่าลูกค้าเปิดอ่านข้อความ
- พนักงานร้านเดียวกันแสกนเพื่อดูข้อมูลและกดยืนยันรับสิทธิ์ ผลสำเร็จใช้สิทธิ์ได้ครั้งเดียว คูปองอายุถึง 24 ชั่วโมงหลังสิ้นสุดเวลาจอง การยกเลิกหรือบันทึกการคืนเงินที่เกิดขึ้นจริงผ่าน RPC ฝั่ง service จะ void คูปองที่ยังไม่ใช้ ส่วนการคืนเงินเองอยู่นอกขอบเขต PR นี้
- หากร้านให้ต่อเวลา ให้คิดเฉพาะชั่วโมงเพิ่มตามราคาปกติที่บันทึกในรายการเดิม และตรวจคิวถัดไป ไม่มีการออกคูปองเพิ่มจากการต่อเวลา ส่วนปุ่มบันทึกต่อเวลาและเรียกเก็บส่วนต่างยังอยู่นอกขอบเขต PR นี้

## ทดสอบในฐานข้อมูลแยก

- ใช้ PostgreSQL ที่ติดตั้ง schema ทั้งหมดแล้ว รัน `psql -v ON_ERROR_STOP=1 -f supabase/tests/promotion_integration.sql` ชุดทดสอบใช้ข้อมูลจำลองและ rollback เมื่อเสร็จ
- เพื่อทดสอบพร้อมกันในฐานข้อมูลทดสอบแบบทิ้งได้ ให้รัน fixture ด้วย `-v promo_concurrency=1` แล้วเรียก `rf_redeem_promotion_voucher` ด้วย token ของ booking `85510000-0000-4000-8000-000000000005` พร้อมกันจากสอง session ในฐานะ `authenticated` ด้วย UID `85510000-0000-4000-8000-000000000001` ผลต้องสำเร็จเพียงครั้งและได้ `ALREADY_REDEEMED` อีกครั้ง
- ทดสอบ worker แบบจำลองด้วย `deno test --allow-env supabase/tests/promotion_worker_test.ts` ซึ่งไม่ส่ง LINE จริง ตรวจ Cron secret, routing, retry key, Flex URL และผลตอบรับ 200/409/500
- ก่อนใช้งานจริงให้ทดสอบ QR และ Flex ด้วย OA ทดสอบบน Android และ iPhone ตรวจสิทธิ์พนักงานต่างร้าน ตรวจ URL ภาพที่ LINE ดึงได้ และทดสอบภาระงานจริง ปัจจุบัน QR ใช้ rate limit ต่อ instance และ token สำหรับลดการใช้งานซ้ำระยะสั้น

## ผลทดสอบของ PR #5

- PostgreSQL แบบแยกผ่านการรัน migration และทดสอบราคาใน QR, การปลอมยอด, โควต้า, สิทธิ์ข้ามร้าน, สลิปที่ยังไม่ยืนยัน, การยกเลิก, คืนเงินและหมดอายุ ทดสอบเรียกยืนยันคูปองจากสอง session ได้ผลสำเร็จหนึ่งครั้งและอีกครั้งตอบ `ALREADY_REDEEMED`
- Chromium จำลองหน้ามือถือผ่านทั้งจองพร้อมโปรและจองปกติ Deno ผ่านการทดสอบ PNG และ LINE worker แบบจำลองสำหรับผล 200, 409 และ 500
- รอผลจาก LINE OA จริง, Android/iPhone จริง และการรับชำระใน staging ก่อนเปิดใช้งานจริง

## ขั้นตอน staging หลังรีวิว

1. สร้างหรือใช้ Supabase staging ของ **ReserveFlow** ที่แยกจาก production ติดตั้ง SQL ฐานถึง 51 แล้วตามด้วย migrations วันที่ 27 พ.ย. ลำดับ 01–04
2. Deploy `promotion-qr` และ `promotion-line-worker` ไป staging ตั้ง `PROMOTION_SITE_URL` เป็น URL preview ที่ปิดท้ายด้วย `/` และตั้ง `PROMOTION_WORKER_SECRET` ผ่าน Secret Manager
3. สำหรับการจองผ่าน LIFF ให้ deploy `booking-line-payment` ใน staging ตั้ง `BOOKING_SITE_ORIGIN` เป็น origin ของเว็บ preview และตั้ง LIFF ของ OA ทดสอบให้ชี้ไปหน้า preview จากนั้นผูก OA ทดสอบกับร้านใน staging
4. ตั้ง Cron ใน staging ส่ง POST พร้อม `x-promotion-worker-secret` จาก Vault ปิดการเรียก worker จากเบราว์เซอร์และใช้ข้อมูลจำลองเท่านั้น
5. ส่งผลทดสอบจากอุปกรณ์จริงให้ผู้ดูแล PR ตรวจ ก่อนอนุมัติ Merge หรือเปิด production
